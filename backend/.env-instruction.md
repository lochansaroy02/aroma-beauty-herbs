# Environment configuration

Everything the backend reads from `.env`, what it does, and what to change when
you move to the VPS.

**The names in `src/lib/env.ts` are the contract.** A variable not read there is
ignored no matter how reasonable it looks — `GMAIL_USER` and `GMAIL_APP_PASSWORD`
sat in this file for a while doing nothing, which is why OTP codes were printing
to the console instead of being emailed.

Only two are required. `DATABASE_URL` and `JWT_SECRET` throw at startup if
missing; everything else has a working default.

---

## 1. Runtime

| Key | Default | Notes |
| --- | --- | --- |
| `NODE_ENV` | `development` | `production` turns on stricter behaviour — see below |
| `PORT` | `4000` | We run `8080`. Must match `API_URL` in `frontend/.env.local` |
| `CORS_ORIGIN` | `*` | Origin of the **Next.js app**, not this server |

`NODE_ENV=production` changes one thing that matters: if SMTP is unconfigured,
sending throws instead of printing the code to the console. In development the
console fallback is a convenience; in production it would mean signup silently
"succeeds" while nobody receives a code — and the code sits in your server logs.

Set `CORS_ORIGIN` to your real frontend domain in production. Leaving it `*` lets
any site call the API with a user's credentials.

## 2. Database

| Key | Required | Notes |
| --- | --- | --- |
| `DATABASE_URL` | **yes** | Postgres connection string |

Two are in the file — the local one is active, the hosted Prisma Postgres one is
commented out. Swap which line is commented to switch. The hosted URL needs
`?sslmode=require`; the local one must not have it.

---

## 3. Auth / JWT

| Key | Required | Default | Notes |
| --- | --- | --- | --- |
| `JWT_SECRET` | **yes** | — | Signs session tokens |
| `JWT_EXPIRES_IN` | no | `7d` | `60s`, `24h`, `7d`… |

**Use a different secret in production.** The one in this file has been on a dev
machine and is not trustworthy. Generate one with:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
```

Changing it invalidates every existing session — everyone is logged out. That is
also the emergency lever if a token ever leaks.

## 5. Email (OTP delivery)

| Key | Default | Notes |
| --- | --- | --- |
| `SMTP_HOST` | *(empty)* | Empty ⇒ codes print to the console (dev only) |
| `SMTP_PORT` | `587` | `587` with `SMTP_SECURE=false`, or `465` with `true` |
| `SMTP_SECURE` | `false` | Must match the port, or the connection times out |
| `SMTP_USER` | *(empty)* | Full email address |
| `SMTP_PASSWORD` | *(empty)* | Gmail: a 16-character **App Password** |
| `MAIL_FROM` | derived from `SMTP_USER` | Visible sender |
| `MAIL_REPLY_TO` | *(empty)* | Optional, but a monitored address helps deliverability |

All three of host, user, and password are needed. A host without credentials is
treated as unconfigured, because Gmail rejects it at `MAIL FROM` with
`530 Authentication Required`.

### Gmail specifics

App Passwords require 2-Step Verification: Google Account → Security → 2-Step
Verification → App passwords. Google displays it as `abcd efgh ijkl mnop`; the
spaces are stripped automatically, so pasting it as shown is fine.

`MAIL_FROM` **must be the same address as `SMTP_USER`**. Gmail can only sign mail
for the authenticated account and silently rewrites anything else. The server
warns at boot when they don't line up.

### Staying out of spam

Gmail SMTP from a personal account cannot get you reliable deliverability. It caps
around 500 recipients/day, forces the From address, and OTPs sent from a
`gmail.com` address to other providers routinely land in spam.

For production, use a provider where you own the sending domain, then add its
**SPF**, **DKIM**, and **DMARC** DNS records. All of these speak SMTP, so only the
values below change — no code changes:

| Provider | Host | Port |
| --- | --- | --- |
| Amazon SES | `email-smtp.<region>.amazonaws.com` | 587 |
| Resend | `smtp.resend.com` (user `resend`, password = API key) | 587 |
| Brevo | `smtp-relay.brevo.com` | 587 |
| Postmark | `smtp.postmarkapp.com` | 587 |

Then set `MAIL_FROM="Aroma Beauty Herbs <no-reply@yourdomain.com>"`.

### Testing

```bash
npm run mail:test                 # sends to SMTP_USER
npm run mail:test you@gmail.com   # sends to that address
```

It prints the resolved settings, verifies the credentials, and sends one real
message. Common failures are decoded for you — a `535` means the App Password is
wrong, a `530` means the credentials never got sent.

## 6. Media storage (local disk)

| Key | Default | Notes |
| --- | --- | --- |
| `MEDIA_ROOT` | `./media` | Where bytes are written. Relative resolves from the process's working directory |
| `MEDIA_BASE_URL` | `http://localhost:<PORT>` | Origin those files are reachable at |

Uploads are written under `MEDIA_ROOT` and served at
`<MEDIA_BASE_URL>/media/<folder>/<file>`. The database stores only the relative
path, so moving the disk or putting a domain in front is a change to these two
values and nothing else.

```
MEDIA_ROOT/products/rose-serum-a1b2c3.jpg
  → http://localhost:8080/media/products/rose-serum-a1b2c3.jpg
```

**On the VPS, put `MEDIA_ROOT` outside the deploy directory.** Otherwise a
redeploy deletes every product image. There is no second copy — this replaced
ImageKit, so back this directory up separately.

```bash
sudo mkdir -p /var/www/aroma/media
sudo chown -R $USER /var/www/aroma/media
```

```
MEDIA_ROOT="/var/www/aroma/media"
MEDIA_BASE_URL="https://api.yourdomain.com"
```

`MEDIA_BASE_URL` must be an origin a **browser** can resolve. `localhost` works
only while you're the only visitor.

### Frontend side

`frontend/.env.local` needs `MEDIA_BASE_URL` too — `next.config.ts` uses it to
allow the host for `next/image`, which refuses any host not listed. Keep the two
in sync or images 400.

### Behind nginx

Serve `/media` straight from `MEDIA_ROOT` so image traffic never wakes Node:

```nginx
location /media/ {
    alias /var/www/aroma/media/;
    access_log off;
    expires 365d;
    add_header Cache-Control "public, immutable";
}
```

Filenames carry a random suffix and are never reused, so caching them forever is
safe.

### Migrating off ImageKit

Already done for the 9 existing files. Kept for reference — it is idempotent, so
re-running only fetches what is missing:

```bash
npm run media:migrate -- https://ik.imagekit.io/your_id
```

## 7. Payments (Razorpay)

| Key | Notes |
| --- | --- |
| `RAZORPAY_KEY_ID` | Real keys look like `rzp_test_…` or `rzp_live_…` |
| `RAZORPAY_KEY_SECRET` | From Settings → API Keys |
| `RAZORPAY_WEBHOOK_SECRET` | From Settings → Webhooks |

The current values are placeholders. Until the key id matches the real pattern,
checkout still records orders but marks them awaiting payment — nothing crashes,
so you can exercise the flow before the business is verified.

`RAZORPAY_WEBHOOK_SECRET` is separate and easy to miss: while it is blank, the
webhook route rejects every call, so `payment.captured` and `payment.failed` never
update an order.

---

## 8. Order handling

| Key | Default | Notes |
| --- | --- | --- |
| `ORDER_RESERVATION_MINUTES` | `30` | Minimum 30 is not enforced; values below 5 are clamped |

How long an unpaid order holds its stock before the sweeper returns it. Long
enough for a slow bank page, short enough that abandoned checkouts don't make the
catalogue read as sold out. The sweeper runs every 5 minutes inside the web
process; `npm run orders:sweep` runs it once from the CLI if you'd rather use cron.

## Production checklist

- [ ] `NODE_ENV=production`
- [ ] Fresh `JWT_SECRET` (not the dev one)
- [ ] `CORS_ORIGIN` set to the real frontend domain, not `*`
- [ ] `APP_URL` and `MEDIA_BASE_URL` on real domains, not `localhost`
- [ ] `MEDIA_ROOT` absolute and outside the deploy directory, with a backup
- [ ] Real Razorpay keys **and** the webhook secret
- [ ] Mail on a provider with SPF/DKIM/DMARC for your domain
- [ ] `frontend/.env.local` `API_URL` and `MEDIA_BASE_URL` updated to match
- [ ] `.env` not committed — verify with `git status` after `git init`
